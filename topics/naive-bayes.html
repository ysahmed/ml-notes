Topic 04 · Classification

Naive Bayes

The probabilistic voter: start with a hunch, multiply in each piece of evidence, and read off the answer — built on one deliberately unrealistic assumption that somehow works anyway.

1. The big idea: start with a guess, update with evidence

Every model so far answers with confidence — a line, a probability, a vote among neighbors. Naive Bayes answers with likelihood: given everything I've seen, how likely is this? It's the natural fit when you already think in odds: "spam is uncommon, but these words are suspicious…"

The whole algorithm

1. Count how often each clue appears in each class. 2. Start from the class's base rate (the prior). 3. For a new case, multiply in the clue by clue. 4. Whichever class ends up more likely wins.

"Training" here is literally counting — no gradient descent, no distance metric, no iteration. That's why it's the classic first text classifier: fast, tiny, and transparent.

Where logistic regression squashes a score into a probability (`w·x + b` → sigmoid), this one multiplies evidence. Both end with a probability between 0 and 1 — they get there by completely different roads, and seeing the second road makes the first one make more sense.

One naming note so the pieces click: the Bayes classifier from Foundations §9 is the ideal rule that can see the true probabilities — nobody gets to be it. What this page builds is a practical estimate of that ideal, made from counts you can actually collect.

2. Bayes' rule in plain English

At the heart is a rearrangement of one tiny equation — so useful it has a name on every line:

Bayes' rule — update a belief with evidence

$$P(A \mid B) = \frac{P(B \mid A) \cdot P(A)}{P(B)}$$

P(A) = the prior — what you believed before seeing B. P(B|A) = the likelihood — how well B fits if A is true. P(A|B) = the posterior — the updated belief after seeing B. P(B) = the evidence's own overall rate (it only rescales — every class gets divided by the same thing, so for picking a winner we can ignore it).

The classic embarrassment that shows why priors matter: a disease hits 1% of people, and a test is 95% accurate. Test positive — how worried should you be? Most people say "95%!" The correct update is about 16%: false alarms among the 99% healthy crowd outnumber real hits among the 1% sick. Take a second independent positive test, though, and the posterior jumps into the high 70s — the evidence finally outruns the prior.

3. Many pieces of evidence: multiply them in

Email isn't one clue, it's twenty. Given Bayes' rule works for one piece of evidence, the obvious move is to update successively — let the posterior after "free" become the prior for "wire", and so on. Algebraically that's just one big product:

The evidence product (spam edition)

$$P(\text{spam} \mid w_1..w_n) \propto P(\text{spam}) \cdot \prod_{i=1}^{n} P(w_i \mid \text{spam})$$

Base rate × one factor per clue. Do the same for ham, then normalize so the two chances add up to 1. (The ∝ means "proportional to" — we dropped the shared P(words) divisor from Bayes' rule, which as noted can't change the winner.)

Contrast it with the score you know: logistic regression adds up weighted evidence (`w·x + b`) — one big juggling act of weights learned by gradient descent. Naive Bayes multiplies per-clue probabilities — each clue is counted on its own, and no optimization is needed at all. Two very different temperaments, both ending in "P(spam) = …".

4. The "naive" leap: an assumption nobody believes

Here's the cheat. Updating evidence one clue at a time is only valid if each new clue is independent of the previous ones — as if "free" appearing told you nothing about whether "wire" would appear too. In real email, words come in gangs ("free money", "meeting room", "wire transfer") — the assumption is obviously false. That's the "naive" in Naive Bayes.

Why does it work anyway?

Because we mostly don't need accurate probabilities — we need the right winner. Naive Bayes often gets the ranking correct even when its actual numbers are nonsense (it will happily report P(spam) = 120% in unnormalized form). It's like a scale that's off by a constant: useless for weighing parcels, perfectly fine for telling which parcel is heavier.

It breaks visibly when clues interact rather than repeat: "New" and "York" are each ordinary, but together they mean a location — a naive product can't represent the pair, so it overcounts the pieces. The fix in practice: hand it smarter clues (bigrams like "new_york") and let it multiply those instead.

5. Two traps: tiny numbers & zero counts

Two things go wrong the moment you multiply real-world probabilities. Both have short, standard fixes:

Trap 1 — the product sinks to the bottom of the sea

  1. Multiply 40 factors, each around 0.1 → roughly 1e-40.
  2. Computers run out of precision below ~1e-308 (or silently hit zero).
  3. Fix: add logarithms instead. log(a·b) = log a + log b, so the product becomes a sum of comfortably sized negative numbers — same ranking, no underflow. Every real implementation does this.

Trap 2 — one zero kills everything

  1. You never saw "meeting" in spam → P("meeting" | spam) = 0.
  2. The whole spam product includes that factor → P(spam | everything) = 0, no matter how incriminating the other words are.
  3. Fix: Laplace smoothing — pretend you saw every word one extra time. Add 1 to every count (or a smaller α), add the vocabulary size to the denominator. Nothing can be zero anymore.

7. When it shines (and when it doesn't)

  • Text, text, text. Spam filters, sentiment, topic tags — its native habitat. Word counts are exactly what it wants to eat.
  • Tiny data & fast retraining. New day, new spam campaign? Recount and you're done — no epochs, no convergence, runs on every prediction in microseconds.
  • An honest baseline. Ten lines of code, interpretable counts, hard to embarrass — the bar every fancier model must clear.
  • Avoid when clues gang up. Strong feature interactions (bigrams, engineered ratios) defeat the independence story — or hand it the interactions as features.

Naive Bayes vs KNN — the two "classics" compared

Both feel instant and old-school, but they're opposites: KNN is lazy (stores everything, computes at prediction time); Naive Bayes eagerly trains by counting, then predicts in one tiny product. KNN asks "who's nearby?"; Naive Bayes asks "which story fits the evidence?".

8. The whole thing in ~30 lines of NumPy

Counts, smoothing, logs, argmax — that's the entire model:

import numpy as np

def nb_fit(X, y, alpha=1):
    """Learn P(class), P(word|class) with Laplace smoothing — just counts."""
    n = X.shape[1]                       # vocabulary size
    log_prior = np.log([ (y == c).mean() for c in (0, 1) ])
    log_lik = np.stack([                  # rows: class 0, class 1
        np.log(((X[y == c].sum(axis=0) + alpha) /
                (X[y == c].sum() + alpha * n)))
        for c in (0, 1)
    ])
    return log_prior, log_lik

def nb_predict(log_prior, log_lik, X):
    """Score each class in LOG space (no underflow), pick the winner."""
    scores = log_prior[None, :] + X @ log_lik.T
    return scores.argmax(axis=1)

# usage: X = word-count rows, y = 0 (ham) / 1 (spam)
# log_prior, log_lik = nb_fit(X_train, y_train)
# preds = nb_predict(log_prior, log_lik, X_test)

The matrix product X @ log_lik.T is the naive product — done with sums of logs instead of multiplications, across every email at once.

9. Cheat sheet

Bayes' rule

$$P(A \mid B) = \frac{P(B \mid A)\, P(A)}{P(B)}$$

prior × likelihood → posterior; the P(B) rescales both rivals equally.

The naive product

$$P(c \mid w_{1..n}) \propto P(c) \prod_i P(w_i \mid c)$$

Assumes clues independent given the class — wrong, but the winner is usually right.

Log trick

$$\log(a \cdot b) = \log a + \log b$$

Sum logs, never multiply tiny probabilities.

Laplace smoothing

$$P(w \mid c) = \frac{\text{count} + 1}{\text{total} + V}$$

Never let an unseen clue zero out a class.

Training = counting

No gradient descent. Means/variances for Gaussian data, word counts for text.

When to use

Text · small data · fast baselines. Avoid when features interact strongly — or feed it the interactions.

The one-sentence version

Start from the base rate, multiply in one factor per clue (in log space, with smoothing so nothing reads zero), and let the bigger number win — an assumption you know is false, in service of a ranking that's usually right.
